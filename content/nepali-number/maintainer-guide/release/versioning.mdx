> Snapshot of the policy as it stands today. Edit in place; never record what changed.

`nepali-number` follows [Semantic Versioning 2.0.0](https://semver.org). The public API is
**every export of the package root, its TypeScript signature, and the string or number it
returns for each input**, plus the published shape (entry points, formats, global name).

## Which bump?

| Change | Bump | Commit prefix |
|---|---|---|
| Remove or rename an export or an option | **major** | `feat!:` |
| Change a parameter, a default, or a return type | **major** | `feat!:` |
| Change the output for an existing input — a word, spelling, spacing, sign, digit, rounding | **major**, unless the next row applies | `feat!:` |
| Fix output that contradicts what the API reference documents | patch | `fix:` |
| Change `exports`, `main`/`module`/`types`, the output formats or the global name | **major** | `feat!:` |
| Drop support for a Node.js version CI tests | **major** | `feat!:` |
| Add an export, an optional option, or an accepted input type | minor | `feat:` |
| Start handling input that previously returned the safe default | minor | `feat:` |
| Export an existing type (`FormatOptions`, …) | minor | `feat:` |
| Faster or smaller, identical output | patch | `perf:` |
| Docs, tests, CI, tooling, internal refactor with identical output | none | `docs:` `test:` `ci:` `chore:` `refactor:` |

A breaking commit carries a `BREAKING CHANGE:` footer that says what consumers must change.

release-please reads these prefixes and proposes the next version in its release pull request
([releasing](./releasing.mdx)). A wrong prefix proposes a wrong version, so the prefix is checked
when a pull request is merged and again before the release pull request is.

## Why output changes are breaking

Applications render these strings and compare them in snapshot tests. Changing
`toNepaliWords(21)` from `"एक्काईस"` to another spelling breaks every snapshot that contains it,
even if the new spelling is better. The exception is output that is wrong *by the package's
own reference*: once the API reference documents a behaviour, code that disagrees with it is a bug.

Entries in [limitations](../../user-guide/dev/api/limitations.mdx) are **documented current behaviour**, not
bugs; changing them is a major unless the owner decides otherwise in the ADR.

## Internal surface

`src/constants.ts` exports (`NEPALI_WORDS`, `NEPALI_SCALES`, …) are **not** re-exported from the
package root. Their shape may change in any release; only what the public functions return is
covered by semver.
