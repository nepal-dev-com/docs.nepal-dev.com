## Context

AI-written code tends to over-comment: restating the code, adding banners and section headers.
Those comments rot as the code changes, and they hide the few comments that matter — the
non-obvious constraints (framework quirks, third-party API limits, build-environment
differences).

Separately, an unbraced `if` body reads as guarded when a second line is added under it, and
the diff looks right. In a filter that decides which pages are published, that is a silent
leak.

## Decision

1. **Comments explain *why*; the code explains *what*.** Default to no comment. Write one only
   for reasoning, trade-offs, edge cases or external constraints that cannot be recovered from
   the code. Prefer a reference to an ADR over prose. One or two lines, directly above what they
   explain. No banners, no `=====` headers.
2. **Configuration files may describe what a key does** (`next.config.mjs`,
   `eslint.config.mjs`, `tsconfig.json`, `.env.example`, CI and deployment manifests), still
   briefly, still linking the governing ADR. `.env.example` documents every variable and never
   its value.
3. **Tooling-consumed documentation stays**: JSDoc/TSDoc on exported public APIs,
   `@ts-expect-error` reasons, pragmas, directives.
4. **Every control-flow branch takes a block**: `if`, `else`, `for`, `while`, `do` bodies are
   braced even for one statement, enforced by ESLint `curly: ["error", "all"]`.

## Options considered

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| A — Why-only comments + mandatory braces (lint-enforced) | Comments stay meaningful; brace rule is mechanical and cheap | Requires discipline from agents | Chosen |
| B — Comment liberally | Feels explanatory | Comments rot and drown the important ones | Rejected |
| C — Braces by convention only | No lint change | Unenforced conventions drift | Rejected |

## Consequences

**Positive**

- The comments that exist are worth reading.
- A class of control-flow bugs is ruled out by lint.

**Negative / accepted trade-offs**

- Slightly more verbose one-line conditionals.

## Content invariants

None directly.

## Security considerations

None — this change touches no data, no endpoint and no secret. (Comments must still never
contain secrets; see ADR-0005.)
