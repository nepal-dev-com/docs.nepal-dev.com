## Context

The owner asked (2026-11-01) that the people in an ADR, its deciders and approvers, be named by
their GitHub username; that an ADR page link to each person's GitHub profile and show their
profile picture if possible; and that agents in consuming repositories ask for a username they
don't already have.

The text side was done on the owner's direct instruction, as a content change: every ADR's
`Deciders` and `Approved by` line, and the template's, reads
`[@puncoz](https://github.com/puncoz)`; `AGENTS.md` §2 and `PROJECT_AGENTS.md` §3 and §7 say to
write people that way and to ask for an unknown username. What remains is a UI change, the
profile picture, and it departs from a rule, so it is this ADR.

The owner chose, from options:

- **Format:** a plain Markdown link, `[@user](https://github.com/user)`, not a component or a
  frontmatter field.
- **Avatar:** loaded live from GitHub, not a copy committed to the repository.

Facts this decision rests on, checked:

- MDX links on docs pages render through `a: createRelativeLink(source, page)` in
  `src/app/(site)/[...slug]/page.tsx`, over Fumadocs' `a: Link` (`fumadocs-ui/dist/mdx.js`).
  Fumadocs' `Link` opens an external link in a new tab (`fumadocs-core/dist/link.js`).
- `https://github.com/puncoz.png` answers `302` to
  `https://avatars.githubusercontent.com/u/7767424?v=4` (`cache-control: no-cache` on the
  redirect); the image is a JPEG with `cache-control: max-age=300`. `?size=40` is passed on as
  `s=40`. Checked with `curl -I` on 2026-11-01.
- The Markdown surfaces (`/<page>.md`, `llms-full.txt`, `static.json`) carry the link as text.
- `AGENTS.md` §8 and ADR-0002 decision 5 say "No binary or externally hosted images".

## Decision

1. **People in an ADR are GitHub usernames.** Every person an ADR names as deciding or
   approving is written as a profile link, `[@user](https://github.com/user)`. The owner is
   `puncoz`. An agent that does not know a person's username asks for it, and never writes a
   display name in its place or guesses one (`AGENTS.md` §2, `PROJECT_AGENTS.md` §3).

2. **A profile link renders as a chip.** On any page, a link whose text is exactly `@user` and
   whose address is exactly `https://github.com/user`, for the same `user` (compared without
   case) and a valid GitHub username (1 to 39 letters, digits or single hyphens, not starting
   or ending with a hyphen), shows as a chip: a 20px round avatar beside `@user`, linking to
   the profile and opening in a new tab like the site's other external links. Every other link
   is unchanged. The site's `a` component checks the shape and hands everything else to
   `createRelativeLink` as today.

3. **The avatar is loaded live from GitHub**:
   `<img src="https://github.com/<user>.png?size=40" width="20" height="20" alt="" loading="lazy" decoding="async" referrerpolicy="no-referrer">`.
   The username's first letter sits behind the image, so while it loads, or if it is blocked or
   missing, the chip shows the letter. The image is decorative: the link's name is its visible
   `@user` text, with the title "@user on GitHub".

4. **Nothing changes in the Markdown surfaces.** The per-page Markdown, `llms.txt`,
   `llms-full.txt` and the search records keep the link as written; no image URL is added.

5. **The one exception to "no externally hosted images".** The avatar in a profile chip is the
   only externally hosted image on the site. `AGENTS.md` §8 says so, and this ADR supersedes
   ADR-0002 decision 5 for it alone.

## Options considered

| Concern | Option | Pros | Cons | Verdict |
|---|---|---|---|---|
| Format | A — a Markdown link, `[@user](https://github.com/user)` | Reads and works anywhere: GitHub, the Markdown routes, an editor; no schema change | The site has to recognise a link's shape | Chosen (owner) |
| Format | B — an MDX component, `<GitHubUser name="puncoz" />` | Explicit | Markdown readers and GitHub see a bare tag | Rejected |
| Format | C — frontmatter, `deciders: [puncoz]` | Validated by the schema | A schema change; every ADR's header rewritten; the header lines lose the names | Rejected |
| Avatar | A — loaded live from `github.com/<user>.png` | Always current; no file to keep; works on any host | Each reader's browser contacts GitHub; an exception to the no-external-images rule | Chosen (owner) |
| Avatar | B — a copy committed to `public/` | No third-party request | Goes stale; a binary file in the repository; another person's picture copied | Rejected |
| Avatar | C — through the Next.js image optimiser (`images.remotePatterns`) | Readers never contact GitHub | Needs a host with image optimisation; no hosting ADR yet; config change | Rejected for now |
| Avatar | D — no avatar, the link only | Nothing new | Not what the owner asked for | Rejected |
| Where | A — any link of exactly that shape, on any page | One rule; a project's own pages get it too | A page that writes such a link outside an ADR also gets a chip | Chosen (owner) |
| Where | B — ADR pages only | Narrowest | A second rule about which pages count | Rejected |

## Consequences

**Positive**

- Each decider and approver is one click from their profile, with their face beside the name.
- ADRs read the same in an editor, on GitHub and on the site.

**Negative / accepted trade-offs**

- Every reader of a page with a chip makes requests to `github.com` and
  `avatars.githubusercontent.com`.
- A person's avatar is whatever they set on GitHub, shown on this site.
- A renamed GitHub account leaves its old links pointing at someone else, or at nothing.

## Content invariants

- **1 (Private stays private).** Unchanged: a username in a public page is public. A private
  project's ADRs are not in `content/` at all.
- **5 (Readable as Markdown).** Kept: the Markdown keeps the link as written (decision 4).
- **Departs from** ADR-0002 decision 5 and `AGENTS.md` §8, "no externally hosted images", for
  the avatar alone (decision 5). That departure is part of what the owner approves.

## Security considerations

- **What leaves the system.** Nothing from the site. Each reader's browser requests
  `github.com/<user>.png` and follows the redirect to `avatars.githubusercontent.com`, sending
  the reader's IP address and user agent. `referrerpolicy="no-referrer"` keeps the page's
  address out of the request. GitHub learns that someone viewed a picture of `user`. This is a
  new boundary crossing, Browser → GitHub, recorded in [`../dfd/system.mdx`](../dfd/system.mdx)
  on implementation.
- **Personal data.** A GitHub username is personal data, public on GitHub. Only the owner's is
  written today. Another person's goes in only with the owner's yes, as `PROJECT_AGENTS.md`
  says.
- **Input.** The username comes from a page's own Markdown, never from a reader. It is checked
  against GitHub's username rules (decision 2) before it is put into a URL, so a link cannot
  build an address on another host or path.
- **Image content.** The picture is controlled by the GitHub account. Shown at 20px, as a
  decorative image, not a link target of its own. Accepted.
- **Content Security Policy.** The site sets none for its pages today. One added later must
  allow `img-src` for `https://github.com` and `https://avatars.githubusercontent.com`; the
  ADR that adds it says so.
- **Residual risk.** GitHub can see which IP addresses load which avatars. Accepted by the
  owner's choice of live avatars over a committed copy or a proxy.
